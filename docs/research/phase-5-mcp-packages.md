# Research: Phase 5 MCP packages

Observed 2026-08-26 in America/Los_Angeles. "Current" below means npm's stable `latest` dist-tag at observation time. Registry metadata, published tarballs, source at recorded commits, first-party documentation, changelogs, and issue reports were inspected. Tarballs were downloaded and unpacked without installing them. Two dependency graphs were resolved with `npm install --package-lock-only --ignore-scripts --omit=dev` in disposable temporary directories. No package lifecycle script ran. No credential store or credential-bearing configuration was accessed.

## Findings

### Recommendation

- **[HIGH | Primary] Build a thin, supervisor-owned Phase 5 wrapper on exact `@modelcontextprotocol/client@2.0.0` and `@modelcontextprotocol/core@2.0.0`. Do not adopt `pi-mcp-adapter@2.29.0` as the production abstraction, and do not add legacy `@modelcontextprotocol/sdk@1.30.0` directly.** The official TypeScript SDK has moved to stable v2 split packages; the adapter itself already depends on those exact v2 packages. Use the adapter as an MIT-licensed behavioral reference and test oracle for transport, OAuth, and compatibility edge cases. [Official v2 migration guide](https://github.com/modelcontextprotocol/typescript-sdk/blob/main/docs/migration/upgrade-to-v2.md), [adapter manifest at published commit](https://github.com/nicobailon/pi-mcp-adapter/blob/66c6c526344ceb7c2e8d22e36b7981a21e600433/package.json)
- **[HIGH | Primary] Keep lifecycle, credential policy, namespace mapping, activation, and bounded teardown in this repository's supervisor boundary.** Official packages supply the protocol and transports. The adapter also supplies Pi UI, config discovery, MCP Apps, Agent Plugins, Unix sockets, keyring storage, scripting, and browser-opening behavior. That is a broad policy surface and a poor ownership match for Phase 5. Its published tarball contains 106 files and 2,801,352 unpacked bytes. [npm registry record](https://registry.npmjs.org/pi-mcp-adapter/2.29.0)
- **[HIGH | Primary] Pin exact versions and committed integrity through the repository lockfile.** The adapter is active but young and fast-moving, including three releases within seven days and a same-day install regression/fix sequence. Exact pins make upgrades reviewable. [release history](https://github.com/nicobailon/pi-mcp-adapter/releases), [v2.28.0 install fix](https://github.com/nicobailon/pi-mcp-adapter/issues/441)

### STDIO, streamable HTTP, and Windows

- **[HIGH | Primary] Adapter `2.29.0` implements STDIO and Streamable HTTP using the official v2 client.** It also includes legacy SSE fallback. HTTP starts as Streamable HTTP and falls back to SSE only for `404`, `405`, `406`, or `415`, with fallback disabled when the newer protocol is pinned or Agent Plugin transport is explicit. A `401` can initialize OAuth and retry. [transport construction](https://github.com/nicobailon/pi-mcp-adapter/blob/66c6c526344ceb7c2e8d22e36b7981a21e600433/server-manager.ts#L500-L591), [HTTP connect and fallback](https://github.com/nicobailon/pi-mcp-adapter/blob/66c6c526344ceb7c2e8d22e36b7981a21e600433/server-manager.ts#L900-L1021)
- **[HIGH | Primary] Official v2 `StdioServerParameters.args` is `string[]`.** Process-launch arguments remain distinct OS argv elements. MCP tool-call `arguments` remain JSON objects on the protocol. Any number, boolean, array, or object coercion issue is therefore at a Pi tool/schema adapter boundary, not the STDIO transport boundary. [official v2 STDIO source](https://github.com/modelcontextprotocol/typescript-sdk/blob/cc4b41617ce3601b1290d67216ea0b194a3cd9ac/packages/client/src/client/stdio.ts)
- **[HIGH | Primary] Native Windows support is intentional but not complete proof of process-tree safety.** Official STDIO uses `cross-spawn`, `shell: false`, `windowsHide: true`, and a Windows-safe default environment. Adapter resolves npm/npx binaries directly, passes argv arrays, opens browser URLs through Windows-specific handling, and includes prebuilt `@napi-rs/keyring` targets for Windows x64, ARM64, and ia32. [official STDIO source](https://github.com/modelcontextprotocol/typescript-sdk/blob/cc4b41617ce3601b1290d67216ea0b194a3cd9ac/packages/client/src/client/stdio.ts), [adapter STDIO path](https://github.com/nicobailon/pi-mcp-adapter/blob/66c6c526344ceb7c2e8d22e36b7981a21e600433/server-manager.ts#L500-L591)
- **[HIGH | Primary] Official STDIO close targets the direct child, not a guaranteed descendant tree.** It closes stdin, waits two seconds, sends `SIGTERM`, waits two seconds, then sends `SIGKILL`. A historical adapter report showed a shell wrapper leaving a descendant alive after Pi exited. That report was Unix-specific, but the ownership limitation also matters for Windows `.cmd`, npm, and npx wrapper chains. [official STDIO source](https://github.com/modelcontextprotocol/typescript-sdk/blob/cc4b41617ce3601b1290d67216ea0b194a3cd9ac/packages/client/src/client/stdio.ts), [adapter issue #24](https://github.com/nicobailon/pi-mcp-adapter/issues/24)
- **[MEDIUM | Primary] Windows credential size was a real adapter failure and has source-level remediation.** Issue #223 reported Windows Credential Manager's 2,560 UTF-16-character blob limit breaking large OAuth records. Current adapter code and changelog describe chunked secure storage. Verify with oversized synthetic tokens in a disposable Windows profile before trusting the fix. [issue #223](https://github.com/nicobailon/pi-mcp-adapter/issues/223), [current OAuth provider](https://github.com/nicobailon/pi-mcp-adapter/blob/66c6c526344ceb7c2e8d22e36b7981a21e600433/mcp-oauth-provider.ts)

### Argument type behavior

- **[HIGH | Primary] Adapter proxy arguments accept either a JSON string or a JSON object.** String input is parsed and rejected if it becomes `null`, an array, or a primitive. This restores object input after a prior compatibility change had made arguments string-only to satisfy tool-schema providers that rejected `patternProperties`. [proxy schema and normalization](https://github.com/nicobailon/pi-mcp-adapter/blob/66c6c526344ceb7c2e8d22e36b7981a21e600433/index.ts#L957-L1023), [changelog](https://github.com/nicobailon/pi-mcp-adapter/blob/66c6c526344ceb7c2e8d22e36b7981a21e600433/CHANGELOG.md)
- **[HIGH | Primary] Direct tools preserve native JSON booleans and numbers.** They only attempt one-layer JSON parsing when the advertised server schema expects an object or array but the model supplied a string. This is pragmatic recovery, but it can change a deliberately string-encoded value when a server's schema and actual behavior disagree. [direct-tool normalization](https://github.com/nicobailon/pi-mcp-adapter/blob/66c6c526344ceb7c2e8d22e36b7981a21e600433/direct-tools.ts#L35-L84)
- **[MEDIUM | Primary] Argument compatibility remains provider-dependent.** Adapter changelog entries include fixes for quote preservation and nested gateway parameters. Phase 5 needs contract tests covering native JSON values, exact strings, nested arrays/objects, quoting, empty object, and invalid inputs across both direct and compact/proxy presentation. Changelog evidence shows known failures were addressed, not that every provider boundary is now correct. [adapter changelog](https://github.com/nicobailon/pi-mcp-adapter/blob/66c6c526344ceb7c2e8d22e36b7981a21e600433/CHANGELOG.md)

### Lifecycle and package-command hang risk

- **[HIGH | Primary] Current adapter is not universally lazy at module load.** If any configured server is `eager` or `keep-alive`, extension registration schedules load-time initialization with a synthetic print context. A Pi command that loads extensions can therefore start MCP work even when its purpose is package management or metadata. Whether current Pi `list` and `update` paths import extension entrypoints needs a disposable end-to-end trial. [load-time initialization](https://github.com/nicobailon/pi-mcp-adapter/blob/66c6c526344ceb7c2e8d22e36b7981a21e600433/index.ts#L555-L576)
- **[HIGH | Primary] Normal session shutdown is explicitly wired.** It aborts the runtime owner, awaits owner shutdown, shuts down state, and stops OAuth resources. Health timers are unreferenced. [session shutdown](https://github.com/nicobailon/pi-mcp-adapter/blob/66c6c526344ceb7c2e8d22e36b7981a21e600433/index.ts#L643-L666)
- **[MEDIUM | Primary] Teardown can still wait without an outer deadline.** `closeAll` aborts pending connects, then awaits every pending connection and close operation. If a transport, wrapper descendant, or SDK close path never settles, the adapter has no manager-level deadline that guarantees Pi can exit. [manager close](https://github.com/nicobailon/pi-mcp-adapter/blob/66c6c526344ceb7c2e8d22e36b7981a21e600433/server-manager.ts#L1166-L1237)
- **[MEDIUM | Primary] Historical reports confirm lifecycle failure modes, but not all reproduce current code.** Issue #222 described eager/keep-alive initialization racing and leaving child processes alive; later ownership fencing addressed the race. Pi issue #4617 described print mode hanging after a response with adapter `2.6.1`, but other extensions and Undici handles were present, so it does not isolate adapter causality. Current changelog says panel commands no longer hang in RPC/JSON/print modes. Treat these as regression-test inputs, not proof that `2.29.0` hangs. [adapter issue #222](https://github.com/nicobailon/pi-mcp-adapter/issues/222), [Pi issue #4617](https://github.com/badlogic/pi-mono/issues/4617), [adapter changelog](https://github.com/nicobailon/pi-mcp-adapter/blob/66c6c526344ceb7c2e8d22e36b7981a21e600433/CHANGELOG.md)
- **[HIGH | Primary] Phase 5 should impose its own bounded close protocol.** Stop accepting calls, abort connect/request work, close transport, wait a short deadline, terminate the process tree, wait again, then record forced cleanup. This requirement follows from inspected await paths and direct-child process handling; it does not require replacing official transport implementation.

### OAuth PKCE, state, and token APIs

- **[HIGH | Primary] Official v1 and v2 client providers expose the primitives needed for Authorization Code plus PKCE.** They cover redirect URL, client metadata/information, tokens and token persistence, code-verifier persistence, credential invalidation, and authorization-server discovery. V2 adds issuer-aware context and stamps plus an authorization-provider layer. [official v2 auth source](https://github.com/modelcontextprotocol/typescript-sdk/blob/cc4b41617ce3601b1290d67216ea0b194a3cd9ac/packages/client/src/client/auth.ts), [official v1 auth source](https://github.com/modelcontextprotocol/typescript-sdk/blob/2d889f2b329e46680ec9bdd565de4616c497825a/src/client/auth.ts)
- **[HIGH | Primary] The host must own OAuth `state` validation.** Official v2 transport documentation says `finishAuth(callbackParams)` validates `iss` but does not validate `state`; callers must compare callback state with their stored value first. Phase 5 must store state per pending authorization attempt, require exact equality, reject missing/unknown/replayed state, and consume it once. [official v2 Streamable HTTP source](https://github.com/modelcontextprotocol/typescript-sdk/blob/cc4b41617ce3601b1290d67216ea0b194a3cd9ac/packages/client/src/client/streamableHttp.ts)
- **[HIGH | Primary] Adapter implements both automatic and manual state checks around the official API.** It creates cryptographically random flow-local state and PKCE verifier values; the callback server reserves and looks up pending state; manual callback completion compares expected state before `finishAuth`. [provider state](https://github.com/nicobailon/pi-mcp-adapter/blob/66c6c526344ceb7c2e8d22e36b7981a21e600433/mcp-oauth-provider.ts#L480-L560), [callback state lookup](https://github.com/nicobailon/pi-mcp-adapter/blob/66c6c526344ceb7c2e8d22e36b7981a21e600433/mcp-callback-server.ts#L218-L279), [manual comparison](https://github.com/nicobailon/pi-mcp-adapter/blob/66c6c526344ceb7c2e8d22e36b7981a21e600433/mcp-auth-flow.ts#L578-L583)
- **[HIGH | Primary] Adapter stores tokens in the OS credential store and binds records to server URL and authorization issuer.** Its public `pi-mcp-adapter/oauth` entrypoint exposes get, inspect, and update token helpers; it intentionally does not expose client secrets, PKCE verifier, or state. The public update capability is still broader than Phase 5 needs. Prefer a narrow repository-owned token-vault interface with no arbitrary token-write command. [public OAuth API](https://github.com/nicobailon/pi-mcp-adapter/blob/66c6c526344ceb7c2e8d22e36b7981a21e600433/oauth.ts#L1-L48), [OAuth provider](https://github.com/nicobailon/pi-mcp-adapter/blob/66c6c526344ceb7c2e8d22e36b7981a21e600433/mcp-oauth-provider.ts)
- **[MEDIUM | Primary] Token refresh needs current-version testing.** Official issue #2510 reported a v1.25.3 mid-session expiry path that did not recover after refresh failure. V2 and adapter code have evolved, so the report is not evidence that v2.0.0 still fails. It identifies a necessary test: expired access token, valid refresh token, rotated refresh token, revoked refresh token, and one controlled reauthorization attempt. [official SDK issue #2510](https://github.com/modelcontextprotocol/typescript-sdk/issues/2510)

### Abandonment and migration evidence

- **[HIGH | Primary] No abandonment signal exists for `pi-mcp-adapter` as of observation.** Same-day release activity, a same-day source push, rapid issue fixes, and continuing downstream use contradict abandonment. [releases](https://github.com/nicobailon/pi-mcp-adapter/releases), [repository](https://github.com/nicobailon/pi-mcp-adapter)
- **[HIGH | Primary] Migration is happening below the adapter.** Official TypeScript SDK v2 replaced the monolithic package with role-specific packages, and adapter `2.29.0` has migrated its client implementation to exact v2 `client` and `core`. That is strong evidence against starting new client work on `@modelcontextprotocol/sdk` v1. [official migration guide](https://github.com/modelcontextprotocol/typescript-sdk/blob/main/docs/migration/upgrade-to-v2.md), [adapter manifest](https://github.com/nicobailon/pi-mcp-adapter/blob/66c6c526344ceb7c2e8d22e36b7981a21e600433/package.json)
- **[LOW | Discovery] No broad downstream migration away from the adapter was found.** Exact GitHub searches for variants of "migrated away from pi-mcp-adapter", "replace pi-mcp-adapter", and "remove pi-mcp-adapter" found one small-project issue title proposing replacement with the official client, but no indexed body or wider pattern adequate for a decision. Negative search evidence is weak because private repositories, unindexed code, and silent removals are invisible.

## Disposable Windows trial results

- [HIGH | Primary] `pi-mcp-adapter@2.29.0` installed with lifecycle scripts disabled and zero audit findings. Disposable RPC `get_commands` and `/mcp status` exited cleanly with no configured server.
- [HIGH | Primary] A deliberately unresponsive eager STDIO server made disposable RPC startup take about seven seconds but still exit within the watchdog and leave no child process. `--list-models` did not load/start the configured extension process. Current package-command hang was not reproduced; the load-time source path remains an ownership mismatch for this platform.
- [HIGH | Primary] The selected official v2 adapter preserves native number/boolean/array/object arguments through a real STDIO fixture, passes Streamable HTTP fixture calls through address-pinned transport, and cleans root plus detached Windows descendants on normal close and aborted connect.

## Contradictions and hidden variables

- **[HIGH | Primary] "Official SDK latest" has two correct answers.** `@modelcontextprotocol/sdk@1.30.0` is latest under the requested package name; `@modelcontextprotocol/client@2.0.0` plus `core@2.0.0` is the current official client architecture. Recording only one would either miss exact package identity or recommend a legacy architecture.
- **[HIGH | Primary] "No install scripts" is version- and graph-specific.** Adapter `2.29.0` and both resolved graphs have no consumer install script, while `2.27.0` did contain a breaking `prepare`. Caret dependencies can resolve differently tomorrow. Lock review remains mandatory.
- **[HIGH | Primary] "Supports Windows" does not mean "kills every Windows descendant."** Prebuilt native keyring targets, cross-spawn, direct argv, hidden windows, and Windows-specific URL handling demonstrate support. None proves cleanup through arbitrary `.cmd`, npm, npx, or server-created process trees.
- **[HIGH | Primary] "Args are JSON" mixes two boundaries.** STDIO command args are strings. MCP tool arguments are a JSON object. Pi/provider tool schemas may force string encoding and adapter recovery. Tests must identify which boundary changed a value.
- **[MEDIUM | Primary] "Closed issue" does not prove fixed behavior on this machine.** Windows credential chunking, load-time ownership, print-mode exit, and token refresh all need disposable Windows verification at exact locked versions.
- **[MEDIUM | Primary] Standard npm and `--legacy-peer-deps` produce different product surfaces.** The former pulls legacy SDK v1 through MCP Apps; the latter suppresses that peer. Explicitly scope MCP Apps instead of choosing architecture through an npm flag.
- **[MEDIUM | Primary] The package is active but concentrated.** Release freshness lowers abandonment probability while one npm publisher and one dominant contributor increase continuity and compromised-publisher impact.
- **[MEDIUM | Inference] Pi package-command hang risk depends on Pi's current loader behavior.** Adapter source shows load-time initialization for eager/keep-alive servers, but a source-only audit cannot prove whether each current Pi package command imports extension entrypoints.

## Survivorship-bias sweep

- **[MEDIUM | Discovery] Failure-focused searches covered:** adapter issues for `hang`, `print`, `shutdown`, `child process`, `Windows`, `Credential Manager`, `args`, `OAuth`, `refresh`, `prepare`, and `pi update`; Pi issues naming the adapter and print mode; official TypeScript SDK issues for refresh and transport lifecycle; exact migration/removal phrases across GitHub.
- **[HIGH | Primary] Concrete adverse cases found:** `prepare` broke extension update in `2.27.0`; eager initialization raced and leaked processes; wrapper descendants survived direct-child shutdown; Windows credential size broke OAuth persistence; an older mixed-extension Pi session hung after print output; official v1 refresh behavior had a reported dead end. Each is reflected above with bounded confidence and version context.
- **[MEDIUM | Discovery] Non-adopter evidence is sparse.** Search results are dominated by setup guides and active adopters.
